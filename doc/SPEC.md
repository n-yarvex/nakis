## 0. 约定

- **字节序**：所有多字节整数均为**大端（网络序）**。
- **关键词**：「必须」= MUST，「不得」= MUST NOT，「应」= SHOULD，「可」= MAY。
- **互操作要求 vs 实现行为**：第 2～9 章中的「必须 / 不得」是线上互操作所必需的；第 16 章是**客户端与配置交换**的互操作格式（与线上协议无关，但客户端集成必须一致）；第 10～12 章描述的是参考实现的**发送策略与隧道寿命策略**（全部不依赖对网络质量的任何测量），换一种实现不影响与对端互通（对端只需要能跳过 PAD 帧、接受任意帧大小），但文中给出了全部参数，方便做行为一致的实现。
- **角色**：*客户端* = 提供 SOCKS5 入口的一端；*服务端* = 接受隧道并代为连接目标的一端。
- **隧道（tunnel）**：客户端与服务端之间的一条 TCP 连接（上面可以套 TLS）。**会话（session）**：隧道上承载的一次「对一个目标地址的 TCP 代理」。一条隧道同一时刻只承载**一个**会话，会话结束后隧道可以被复用承载下一个（第 6 章）。
- **协议版本**：本文描述 `HelloVersion = 1`，认证标签 `nakis/auth/v1`。

## 1. 总览与分层

```
应用 ──SOCKS5──▶ 客户端 ══ 隧道: TCP ▸ [TLS1.3, 可选 ECH] ▸ nakis 帧 ══▶ 服务端 ──TCP──▶ 目标
```

一条隧道的生命周期：

```
TCP 建立 → (TLS 握手) → 首帧：[Proof 56B][Hello]… → 会话数据 ⇄ → 结束标记交换(NAP) → (复用) Hello… → … → 关闭
```

- 线上只有一种命令（`CmdHug = 1`）。目标是普通地址时就是 **TCP CONNECT 代理**；目标是**魔术地址** `udp.nakis.arpa` 时，这条隧道改为承载一个 UDP 关联（UoT，第 17 章）。没有 BIND，没有通用多路复用。
- 没有类型字节、序号、窗口：可靠有序交给 TCP，会话内的字节流原样搬运。
- **支持半关闭**：两个方向各自独立收尾，一端发完不会截断另一端还没传完的数据（第 5.4、5.5 节）。

## 2. 传输层：明文 / TLS / ECH

客户端与服务端的 `tls` 选项必须一致（`false` = 明文 TCP，`true` = TLS）。两端没有协商机制，不一致时握手/首帧必然失败。

### 2.1 明文模式

直接在 TCP 上跑 nakis 帧。此模式下 Proof 的绑定值为空（第 4 章），没有保密性、没有服务端身份认证、路径上的攻击者可以在 Proof 之后接管连接。仅建议用于内网或外层另有加密隧道的场景。

### 2.2 TLS 模式

| | 客户端（`secure.go: TLSClientConfig`） | 服务端（`secure.go: TLSServerConfig`） |
|---|---|---|
| 最低版本 | TLS 1.2；**开启 ECH 时为 TLS 1.3** | **TLS 1.3**（所以客户端的 1.2 实际无法完成握手） |
| ALPN | 发送 `["h2", "http/1.1"]` | 只接受 `["http/1.1"]` |
| 动态记录大小 | 关闭（`DynamicRecordSizingDisabled = true`） | 同左 |
| 会话恢复 | 客户端缓存 64 条（LRU） | Go 默认（票据开启） |
| 证书 | 见下（指纹或 CA 校验） | `tls_cert` / `tls_key`（PEM） |
| ServerName | `sni`（开 ECH 时为内层真实名字） | — |

**证书校验（客户端）**

1. `tls_pins` 为空：使用系统根证书做标准校验，校验的主机名为 `sni`；此时 `sni` 必须非空。
2. `tls_pins` 非空：关闭标准校验（`InsecureSkipVerify = true`），改用自定义校验：取服务端发送的**叶子证书**，计算其 `SubjectPublicKeyInfo`（DER）的 **SHA-256**，必须等于某个 pin；否则握手失败。pin 的文本形式为 64 位十六进制（大小写不限、允许 `:` 分隔，内部会去掉冒号并转小写，`secure.go: normalizePin`）。**该模式不检查证书有效期、域名、签发链。**

**记录层批量器（`wire.go: Batcher`，实现细节，不影响互通）**：TLS 下每个 nakis 帧用一次 `Write`。当帧长度 ≤ 16384 字节（`recordPlain`）时一帧对应一条 TLS 记录；大于 16384 时，Go 的 TLS 会拆成多条记录，批量器把这些记录合并成一次底层 `Write`。（性能影响见 TESTING.md，在测试机上差异落在噪声内。）

### 2.3 ECH

- ECHConfig 版本号 `0xfe0d`。
- 客户端配置项 `ech_config` = **ECHConfigList** 的 base64（标准 base64，带填充）；服务端 `ech_keys[].config` = 单个 **ECHConfig** 的 base64，`key` = 32 字节 X25519 私钥的 base64，`retry` = 是否作为 retry 配置下发。
- 参考实现生成的 ECHConfig 内容（`secure.go: NewECH`）：

```
ECHConfig        = version(2)=0xfe0d  length(2)  contents
contents         = config_id(1)
                   kem_id(2)=0x0020                      // DHKEM(X25519, HKDF-SHA256)
                   public_key_len(2) public_key(32)
                   cipher_suites_len(2)=8
                     { kdf_id=0x0001 aead_id=0x0001 }    // HKDF-SHA256 + AES-128-GCM
                     { kdf_id=0x0001 aead_id=0x0003 }    // HKDF-SHA256 + ChaCha20-Poly1305
                   maximum_name_length(1)=64
                   public_name_len(1) public_name
                   extensions_len(2)=0
ECHConfigList    = list_len(2) ECHConfig
```

- 外层 SNI = `public_name`，内层 SNI = 客户端 `sni`；开启 ECH 必须设置 `sni`，且协议版本固定为 TLS 1.3。
- 服务端可以配置多个 `ech_keys`（轮换时新旧并存）。
- **客户端不会自动采用服务端返回的 retry 配置**：ECH 被拒时握手失败，按一次拨号失败处理（参考实现没有处理 `ECHRejectionError`）。

### 2.4 TLS 绑定值（Exporter）

TLS 模式下，双方各自在握手完成后导出：

```
binding = TLS-Exporter(label = "nakis/bind", context = 空串(长度 0), length = 32)
```

标准 exporter（RFC 5705 / RFC 8446 §7.5），Go 中为 `ConnectionState.ExportKeyingMaterial("nakis/bind", nil, 32)`。明文模式下 `binding` 为空字节串（长度 0）。`binding` 用于 Proof（第 4 章），使证明只对当前这一次 TLS 会话有效。

## 3. 帧格式

隧道上的一切（TLS 握手完成之后，或明文模式下从第一个字节开始）都是帧序列：

```
frame = length(2, uint16 BE)  body
```

| `length` | 名称 | 含义 |
|---|---|---|
| `0x0000` | **NAP** | 会话结束标记，没有 body（`Tunnel.Nap`，`ErrNap`） |
| `0x0001`–`0xFFFE` | **DATA** | body 为 `length` 字节的会话字节流片段（`FrameMax = 0xFFFE`） |
| `0xFFFF` | **PAD** | 后接 `pad_len(2)` 与 `pad_len` 字节随机填充；接收方**必须丢弃**（`Tunnel.pull`） |

规则：

1. **DATA 帧边界没有语义**。接收方把连续 DATA 帧的 body 拼成一条字节流，Hello、应答、会话数据都从这条字节流里解析，允许一个逻辑消息横跨多个帧、一个帧包含多个消息。**唯一例外**是首帧（第 4.3 节）。
2. **PAD 可以出现在任意两个帧之间**（包括会话开始之后的任意位置），接收方一律跳过。PAD 总开销 = `4 + pad_len` 字节，`pad_len` 取 0～65535，内容为密码学随机字节（`SendWirePad`）。发送方只会把 PAD 紧跟在一个 DATA 帧之后，**在同一次底层写入里**发出（所以 TLS 下它们在同一条记录里）。
3. **首帧必须是 DATA**，且首帧长度必须 < `0x4100`（即首字节 < `0x41`）；`0xFFFF`（PAD）、`0x0000`（NAP）或首字节 ≥ `0x41` 的首帧，服务端一律按「非 nakis 流量」处理（第 7 章）。参考实现的客户端保证首帧长度不超过 16382（`ShapeCap`），这样首帧恰好能放进一条 TLS 记录（2 字节长度头 + 16382 = 16384）。
4. 隧道在**会话之间**（即一次 NAP 交换之后、下一个 Hello 之前）收到 NAP 时，服务端把它当作隧道结束（`serveOne` 读 Hello 时遇到 `ErrNap` 返回错误并关闭隧道）。
5. 接收方对帧长度没有别的限制；发送方的 DATA 帧不得超过 `0xFFFE` 字节（`ErrOversize`）。参考实现下行方向的第一个 DATA 帧的上限为 `0xFFFE`，其中第 1 字节是应答码（见 5.2），所以服务端单次读取的数据量上限是 `PackCap = 0xFFFD = 65533`。

## 4. 认证证明（Proof）

### 4.1 格式（56 字节，`ProofSize`）

```
proof = timestamp(8)  nonce(16)  mac(32)

timestamp = 发送时刻的 Unix 纳秒时间戳，uint64 BE
nonce     = 16 字节密码学随机数
mac       = HMAC-SHA256( key = uuid_raw(16 字节),
                         msg = "nakis/auth/v1" ‖ timestamp(8) ‖ nonce(16) ‖ binding )
```

- `uuid_raw`：配置里的 `uuid` 去掉所有 `-`，要求恰好 32 个十六进制字符（大小写不限），解码成 16 字节（`ParseUUID`）。连字符的位置不做校验。
- `binding`：第 2.4 节，明文模式为空。
- 字符串 `"nakis/auth/v1"` 为 13 个 ASCII 字节，无结尾 `\0`。

### 4.2 校验算法（服务端，`proof.go: Guard.Accept`）

按**严格的顺序**执行，任一步失败即拒绝（拒绝后的行为见第 7 章）：

1. 长度必须恰为 56，否则 `ErrBadMac`。
2. 重新计算 `mac`，用**常量时间**比较（`hmac.Equal`），不等则 `ErrBadMac`。
3. 时间窗：`|服务端当前时间 − timestamp| ≤ 30 s`（`ProofWindow`），否则 `StaleError`（带偏差值，用于告警日志）。
4. 启动检查：`timestamp < 服务端进程启动时刻 − 1 s` 则 `ErrReplay`。这使得服务端重启后，重启之前抓到的证明无法被重放。
5. 重放检查：以 `nonce`（16 字节）为键查「已见」表，存在则 `ErrReplay`。
6. 容量检查：已见表条目数 ≥ 262144（`seenLimit = 1<<18`）则 `ErrFull`（**宁可拒绝也不放行**）。
7. 全部通过后才把 `nonce` 记入已见表，记录时间为当前时间。

已见表的清理：每次校验时若当前时间超过下一次清理时间，则扫描并删除记录时间距今超过 65 s（`keepSeen = 2×30s + 5s`）的条目，然后把下一次清理时间设为 +10 s。

### 4.3 Proof 的位置

- Proof **必须**位于一条隧道上**第一个 DATA 帧**的 body 开头（前 56 字节），并且只在隧道的第一个会话中出现一次；复用隧道上的后续会话不再带 Proof（客户端用 `Tunnel.sealed` 标志控制）。
- 首帧 body 长度必须 ≥ 56，否则按校验失败处理。首帧里 Proof 之后的字节（可能为空）是会话字节流的开头（通常就是 Hello 以及应用的最初几个字节）。**客户端不等待任何确认**：Proof、Hello、应用数据可以在同一次写入中发出。
- 首帧可以恰好是 56 字节（只有 Proof），此时 Hello 在后续帧里。

### 4.4 防护效果（要点）

重放同一段字节：被 nonce 表或启动检查拒绝；转发到另一条 TLS 会话：`binding` 不同，`mac` 不匹配；跨服务端时间偏差 > 30 s：被拒；暴力猜测：需要 128 位 uuid。明文模式下没有 `binding`，因此只有时间窗 + nonce 的防重放。

## 5. 会话：请求、应答、结束

### 5.1 Hello（请求）

Hello 是会话字节流的开头（紧跟在 Proof 之后，复用隧道上则是会话流的开头）：

```
hello = version(1)=0x01  cmd(1)=0x01  id_len(1)  [id(id_len)]  host_len(1)  host(host_len)  port(2)
```

| 字段 | 要求 |
|---|---|
| `version` | 必须为 `0x01`，否则服务端关闭隧道 |
| `cmd` | 必须为 `0x01`（`CmdHug`，TCP 代理），否则关闭隧道 |
| `id_len` | 保留字段。客户端固定发 `0`；服务端若收到 > 0，**读取并忽略**这么多字节 |
| `host_len` | 1～255；`0` 则服务端关闭隧道 |
| `host` | 目标主机文本：域名（原样字节，不做 IDNA 转换）或 IP 字面量（IPv4 点分十进制；IPv6 为不带方括号的标准文本，由 Go 的 `net.IP.String` 格式化，IPv4 映射地址会输出成 IPv4 点分形式） |
| `port` | 目标端口，uint16 BE |

示例：`example.com:443` → `01 01 00 0b 65 78 61 6d 70 6c 65 2e 63 6f 6d 01 bb`（17 字节）。

服务端拼出的目标地址为 `net.JoinHostPort(host, port)`（IPv6 自动加方括号）。**域名解析发生在服务端**，客户端不做本地 DNS。

### 5.2 应答（服务端 → 客户端）

应答是下行字节流的第一个字节：

| 首字节 | 含义 | 后续 |
|---|---|---|
| `0x00` | **Cozy**：成功 | 无；其后紧跟目标的下行数据（如果有） |
| `0x02` | **Oops**：失败 | `code(1) msg_len(1) msg(msg_len)`；`msg` 至多 250 字节，内容为底层错误文本；`code` = 底层 `syscall.Errno` 的低 8 位，没有则为 0 |
| 其他 | 协议错误 | 客户端报错并关闭隧道 |

关键时序（实现者务必注意）：

- **应答不是在目标连接成功时立即发送的**，而是和**第一批目标下行数据**一起发出（`0x00` 作为第一个 DATA 帧的首字节，`nest.write`）；如果目标在发送任何数据前就结束了，服务端会单独发一个只含 `0x00` 的 DATA 帧，随后发送 NAP（`nest.sendNap`）。
- 因此客户端**不能**把「是否收到 `0x00`」当作「目标是否可连」的信号去阻塞上行；参考实现里上行（Hello + 应用数据）总是立即发出，不等应答。
- 失败（拨号失败、被私网规则拒绝）时服务端发送一个 Oops（经 `Send`，不经整形），**随后关闭隧道**（该隧道不可复用），不发送 NAP。Oops 与成功应答互斥：同一会话里服务端只会发其中之一。

### 5.3 数据阶段

应答之后双方各自把对端的 DATA 帧 body 原样交给本地连接（客户端交给应用，服务端交给目标）。两个方向完全独立、互不等待。

### 5.4 结束：NAP 交换

NAP（`0x0000`）是「我这个方向的数据到此为止」的标记，也就是线上的半关闭信号。**每一方在会话中发送且只发送一个 NAP，并读到对端的 NAP**，之后流恰好停在帧边界上，隧道才可以被复用（第 6 章）。两个方向的 NAP 彼此**不必同时**：先发的一方只是自己不再发送，仍然继续接收，直到对端的 NAP 到来（或超时）。

**服务端视角**（`server.go: nest`）：

1. **目标先结束**（读到 EOF，目标不再发送）→ 把已缓冲的数据发完（`gate.Flush`）→ 发 NAP（若尚未发过应答字节则先发 `0x00`）。之后**继续**把客户端的上行写给目标（目标可能还在读），等待客户端的 NAP；等待期间隧道读超时为 `half_close_timeout`，每收到一帧就重新计时。收到 NAP 后上行写完，隧道可复用。
2. **客户端先结束**（先收到客户端的 NAP）→ 把已收到的上行数据写完，对目标连接做 **`CloseWrite`**（只发 FIN，不关读）→ **继续读目标并转发**，直到目标 EOF，再发自己的 NAP，最后才关闭目标。这段读目标的超时同样是滚动的 `half_close_timeout`。因为客户端的 NAP 已经读到，不再等待。
3. **目标异常结束**（复位、读超时等非 EOF 错误）→ 视为中止：关闭目标，丢弃未写出的上行队列，发 NAP，以 **5 秒**（`serverDrain`）为读超时等待客户端的 NAP；收到则隧道可复用，否则关闭。
4. 任何隧道读写错误 → 标记 broken，隧道关闭，不复用。

**客户端视角**（`client.go: shuttle / upstream / downstream`）：

1. **应用先结束**（读到 EOF，应用不再发送）→ 把缓冲的上行数据发完 → 发 NAP → **继续**把下行数据交给应用，直到服务端的 NAP。等待期间隧道读超时为 `half_close_timeout`（滚动，每收到一帧重新计时）。
2. **服务端先结束**（先收到服务端的 NAP）→ 对应用连接做 `CloseWrite`（把 FIN 传给应用），**继续**读应用的上行并转发，直到应用也结束（读超时为滚动的 `half_close_timeout`），然后发自己的 NAP。
3. **应用整个关闭**（往应用写下行数据时失败）：此时下行已无处可送，客户端立即发 NAP 并改用**排空窗口**（`Kitten.drainWindow`）：`max(500 ms, 2 × 平均握手 RTT)`，上限 5 s（`clientDrain` = 500 ms，`maxDrain` = 5 s；平均握手 RTT 是客户端对所有已测地址握手延迟的平均值，没有样本时按 0）。窗口内收到服务端 NAP 则隧道仍可复用，否则关闭。这一条保证了「用户取消一个大下载」不会让服务端继续灌数据到半关闭超时。
4. 会话结束时若还没发过 NAP 且隧道没坏，补发 NAP。

**NAP 本身不做填充**：它是一个独立的 2 字节 `00 00` 写入（TLS 下一条 24 字节的记录），见第 15 章。

### 5.5 半关闭语义

| 场景 | 行为 |
|---|---|
| 应用 `shutdown(SHUT_WR)` 后继续读 | 目标收到 FIN，目标的响应完整传回应用；两边都收尾后隧道复用 |
| 目标 `shutdown(SHUT_WR)` 后继续读 | 应用收到 FIN，应用后续的上行完整传给目标 |
| 应用 / 目标整个关闭（`close`） | 对端在读侧看到的和半关闭一样是 EOF；写侧的区别要等到真的写失败才知道：客户端往已关闭的应用写失败时走 5.4 客户端第 3 条；服务端往已关闭的目标写失败时终止上行（丢弃队列），并等客户端 NAP |
| 目标复位（RST） | 中止（5.4 服务端第 3 条），不能做到「FIN 与 RST 都忠实传给应用」，应用端只会看到 FIN |
| 半关闭后对端一直沉默 | 滚动超时 `half_close_timeout`（默认 2 分钟）到点收尾：服务端关目标，客户端关隧道，不复用 |

两点说明：

- **线上字节格式没有变化**（`HelloVersion` 仍为 1，NAP 仍是 `00 00`），变的是两端收到 NAP 之后做什么。旧服务端收到客户端 NAP 会直接关闭目标，所以新客户端对旧服务端仍能工作，只是没有半关闭保证；旧客户端对新服务端则会因为只等一个很短的排空窗口而截断较慢的响应。**两端应一起升级**。
- 无法区分「应用 `close()`」和「应用 `shutdown(SHUT_WR)`」是 TCP 本身的限制；参考实现按「先当作半关闭，写失败再转为排空」处理，代价是应用真的整个关闭、而目标又恰好一直沉默时，服务端会在目标上多挂一个 `half_close_timeout`。

## 6. 隧道复用

一个会话**正常**结束（双方各发过且各读到一个 NAP，没有任何错误）后，隧道回到「等待 Hello」状态，可承载下一个会话：

- 客户端把隧道放回池中（第 11 章），下一个会话取出后直接发送 `Hello`（不再带 Proof）。
- 服务端在两个会话之间，把 TCP 读超时设为 `idle_timeout`（默认 2 分钟）；超时没收到下一个 Hello 则关闭隧道。
- 下列情况**不可复用**，必须关闭隧道：Oops；读写错误；超时；没有完整交换 NAP；NAP 之后接收缓冲里还有任何未消费的字节（`Tunnel.Dirty`）；这条隧道的**随机寿命**已到（次数或字节，见第 12 章）；配置的 `pool_max_uses` 硬上限已到；池已满。
- 池中闲置的隧道由一个后台 goroutine 持续读取（探测对端是否关闭/复位）；隧道被取出时先停止这个读取，若发现已死就丢弃（`Tunnel.Watch`）。
- 每个新会话都会**重新生成**整形计划（第 10 章），复用隧道也一样。

### 6.1 复用判据（客户端 `purrConn.release`）

隧道只有在下列**全部**成立时才放回池中，任何一条不成立就关闭：未被标记 broken；本会话已发出 NAP；本会话已读到对端 NAP；接收缓冲干净（`Dirty() == false`：没有被预读的残余字节，没有未交付的片段，`bufio` 里没有缓冲数据）；随机寿命未用完；使用次数未达 `pool_max_uses`。

### 6.2 NAP 异常与会话隔离

协议里**没有会话编号**，隔离完全依赖「一条隧道同一时刻只有一个会话 + 会话之间以一次 NAP 交换为界 + 任何偏差都关闭隧道」。下表是各种异常的结果（对应参考实现里的故障注入测试，见 TESTING.md）：

| 异常 | 谁检测 | 结果 |
|---|---|---|
| 服务端 NAP 之后紧跟多余字节（同一次写入里） | 客户端 `Dirty()` | 隧道关闭，不入池 |
| 隧道在池中闲置时收到任何字节 | 池里的观察者 | 标记死亡，取用时丢弃 |
| 服务端始终不发 NAP | 客户端等待超时（`half_close_timeout`，应用已整个关闭时为排空窗口） | 隧道关闭 |
| 帧在中途被截断 | 读取错误 | 隧道关闭 |
| NAP 在超时之后才到 | 客户端已放弃（读超时 → broken） | 隧道关闭，迟到字节不会被任何会话读到 |
| 客户端在 NAP 之后立刻发垃圾 | 服务端读 Hello 失败（版本/命令/长度非法） | 隧道关闭，**不会产生任何目标连接** |
| 客户端没发 NAP 就发下一个 Hello | 服务端 NAP 排空 | 服务端读并丢弃直到 NAP 或 5 s 超时，随后关闭；该 Hello **不会**被当作新会话执行 |
| 客户端从不发 NAP | 服务端 5 s 超时 | 隧道关闭 |
| 应用提前关闭 / 目标提前关闭 / 半关闭 / 大块数据在途 | 双方 NAP 交换 | 先收尾再复用；收尾失败则按上面各行关闭 |

保证的范围：**诚实对端 + 上表任一异常，都不会让一个会话的字节出现在另一个会话里**。不保证的范围：已认证的对端如果在**下一个会话的 Hello 发出之后**才主动注入字节，该字节与合法应答无法区分（协议没有会话编号）；明文模式下路径上的攻击者可以做同样的事（TLS 模式下记录层的完整性校验会拒绝）。参考实现对 480 个并发的、带随机提前关闭、目标提前关闭、大块数据的会话（明文与 TLS 各一轮）做过隔离压测，两端都没有观察到异常字节（TESTING.md）。

## 7. 服务端接入流程与诱饵（抗主动探测）

目标：任何不是合法 nakis 客户端的连接，看起来都像是一台普通的 nginx 站点。

### 7.1 接入流程（`server.go: handleConn / welcome / admit`）

```
accept → [槽位检查] → [TLS 握手(handshake_timeout)] → 读首帧 → 校验 Proof → 进入会话循环
```

1. **槽位**：同时处理的连接数达到 `max_conns` 时，新连接被直接关闭（不读不写），并输出一条节流后的警告。
2. **TLS 握手**（仅 TLS 模式）：超时 `handshake_timeout`；失败则直接关闭（TLS 库自己的行为，不输出诱饵页）。握手后导出 `binding`。
3. **读首帧**（`Tunnel.ReadFirst`）：
   - 最多等待 `idle_timeout` 读到 2 字节长度头。
   - 若 `首字节 ≥ 0x41`，或长度为 `0`（含 NAP），→ **非 nakis 流量**，把已读的 2 字节作为前缀交给诱饵。（`0xFFFF` 的首字节是 `0xFF`，同样落入这里。）
   - 否则读取 `length` 字节的 body，超时为 `min(handshake_timeout, 3 s)`。读到完整帧则进入校验；**超时**则把已读的字节作为前缀交给诱饵；其他读错误（EOF、复位）则静默丢弃连接。
4. **校验**：body 长度 < 56 → 诱饵；`Guard.Accept` 失败 → 诱饵（并记一次「被拒」计数，见 7.3）；成功则 body 里 56 字节之后的部分作为字节流开头放回（`Tunnel.Unread`）。
5. 进入会话循环（第 5、6 章）。

### 7.2 诱饵（`decoy` / `decoyReply`）

1. 设置 1 秒（`decoyWait`）的读写截止时间；读取并累积字节，直到出现 `\r\n\r\n`、累计 ≥ 4096 字节、或读出错。
2. 根据累积内容的**第一行**生成一个 HTTP/1.1 响应然后**关闭连接**：

| 请求行 | 响应 |
|---|---|
| 方法 ∈ {`GET `,`HEAD `,`POST `,`PUT `,`DELETE `,`OPTIONS `,`PATCH `,`CONNECT `,`TRACE `,`PRI `}，且路径为 `/` 或 `/index.html`（后面紧跟空格） | `200 OK`，正文为 nginx 欢迎页（`HEAD` 不带正文） |
| 方法在上表中，路径为其他 | `404 Not Found`，nginx 风格错误页 |
| 其他（不是 HTTP 请求行） | `400 Bad Request`，nginx 风格错误页 |

响应头：`Server: nginx`、`Date`（UTC，HTTP 日期格式）、`Content-Type: text/html`、`Content-Length`、`Connection: close`。TLS 模式下整个响应在 TLS 里发出。

**实测行为（真实二进制，明文模式；TESTING.md 有同一组数据）：**

| 探测 | 响应 | 耗时 |
|---|---|---|
| `GET / HTTP/1.1` + 头部 + 空行 | 200 欢迎页 | 立即 |
| `GET /admin …` | 404 | 立即 |
| `HEAD /` | 200，无正文 | 立即 |
| 随机字节 + `\r\n\r\n` | 400 | 立即 |
| 5000 字节无换行乱码 | 400 | 立即（≥ 4096 字节触发） |
| 40 字节无换行乱码 | **无响应，1 秒后关闭** | 1.0 s |
| 请求行完整但没有空行 | **无响应，1 秒后关闭** | 1.0 s |
| 仅 1 字节 `0x00`（还差 1 字节凑不成长度头） | 无响应，连接保持（实测 3 秒内未被关闭；按代码为 `idle_timeout`，默认 2 分钟） | ≥ 3 s |
| 长度头声明 64 字节但只给 10 字节 | 无响应（3 秒 body 超时 + 1 秒诱饵等待后静默关闭） | 4.0 s |
| **合法 nakis 客户端但 Proof 错误（错 uuid / 重放 / 时钟偏差）** | 无响应，1 秒后关闭（诱饵在等一个永远不会来的 HTTP 请求头，见下方原因） | 1.0 s |

> 原因：诱饵等待截止时间同时约束写入，所以「等满 1 秒仍没读到完整请求头」时，响应的写入也会因超时失败。这与真实 nginx「请求头不完整就一直等到 client_header_timeout」的行为方向一致，但时间不同（见第 15 章）。

### 7.3 被拒计数与告警

每次被拒累加一个计数，并在第一次被拒后 1 分钟输出一条汇总告警「过去一分钟拒绝了 N 个没有有效证明的连接」；若是 `StaleError`（时钟偏差），额外输出一条带偏差值的告警（至多每 10 秒一条）。这些只影响日志。

## 8. 服务端出站规则

### 8.1 解析与拨号（`dialTarget`）

1. `host` 若是 IP 字面量则直接使用，否则经 DNS 缓存解析（TTL 60 s，同一名字的并发解析合并为一次；解析失败时若有旧答案则继续使用旧答案 5 秒，没有旧答案则缓存错误 5 秒；缓存容量 8192，满了随机淘汰一项）。DNS 服务器由 `dns` 配置指定（按顺序尝试，每个连接超时 5 秒）；空则用系统解析器。
2. 把地址 **IPv4/IPv6 交错排列**（`Interleave`），最多取前 4 个。
3. 只有 1 个地址则直接拨号；多个则**错峰竞速**：第 *i* 个（从 0 起）延迟 `i × 120 ms` 启动，第一个成功的获胜，其余取消，已经建立的落选连接被关闭。
4. 拨号超时 `dial_timeout`；TCP 保活 `keepalive`；可选设置拥塞控制（Linux）。

### 8.2 私网拦截（`isPrivate`，在拨号的 `Control` 回调里对**实际要连接的 IP**检查）

当 `allow_private = false`（默认）时，目标 IP 命中下列任一类即拒绝，并以 Oops 返回 `target address is private; set allow_private to permit it`：

回环地址、私网地址（10/8、172.16/12、192.168/16、fc00::/7）、链路本地单播（169.254/16、fe80::/10，**含云厂商元数据地址 169.254.169.254**）、链路本地组播、未指定地址（0.0.0.0、::）、组播地址。

因为检查发生在连接建立前的最后一刻，所以对 IP 字面量、域名解析结果、DNS 重绑定（解析到私网）都有效。**不在拦截范围内**：100.64.0.0/10（运营商级 NAT）、广播地址 255.255.255.255、文档保留段等。

### 8.3 中继（`nest`）

- 下行（目标 → 隧道）：每次从目标读至多 `PackCap` 字节。读到 ≥ 32766 字节（`PackCap/2`）的大块直接作为一个帧写出（先冲掉发送调度器里已有的数据以保序）；较小的块交给发送调度器（第 10 章）。
- 上行（隧道 → 目标）：收到的 DATA 帧先放进队列，另一个协程把队列里的帧**合并**成至多 `merge_pack` 字节的一次 `Write` 写给目标。队列字节数达到 `max_queue` 时，停止读取隧道（TCP 反压到客户端）。
- 目标写失败：会话结束。

- 目标先结束或客户端先结束时的收尾顺序、半关闭与超时见 5.4 与 5.5。

### 8.4 其他

- 每个连接：TCP keepalive `keepalive`（入站与出站都设置）；`handleConn` 内部 `panic` 会被捕获并记录。
- 关闭：收到信号后停止监听；空闲（两个会话之间或尚未发出请求）的隧道立即关闭，进行中的会话最多等 `shutdown_timeout`，超时则强制关闭剩余连接（包括到目标的连接），再最多等 5 秒让协程退出，仍未退出则记录错误后放弃等待。UDP 关联在收到退出信号时立即结束。

## 9. SOCKS5 入口（客户端）

`client.go: SocksRequest`。只实现了最小子集：

1. 读 `VER NMETHODS METHODS…`：`VER` 必须为 5；**不检查客户端提供的方法列表**，一律回复 `05 00`（无认证）。
2. 读请求 `VER CMD RSV ATYP ADDR PORT`：`VER` 必须为 5；ATYP = 1（IPv4）、3（域名，长度 1～255）、4（IPv6）；其他 ATYP 回复 `05 08 …`（地址类型不支持）并断开。
3. `CMD` = 1（CONNECT）或 3（UDP ASSOCIATE，第 17 章）；其他（含 BIND）回复 `05 07 …`（命令不支持）并断开。
4. **CONNECT：读完请求后立即回复成功** `05 00 00 01 00 00 00 00 00 00`（绑定地址固定为 0.0.0.0:0），此时隧道还没建好；之后的失败（拨号失败、服务端 Oops）只会表现为连接被关闭，没有 SOCKS 错误码。目标主机恰好是魔术地址 `udp.nakis.arpa` 的 CONNECT 请求被直接拒绝。
5. **UDP ASSOCIATE：隧道就绪后**才回复，回复里的绑定地址是 UDP 中继的地址（见 17.6）；取不到隧道时回复 `05 01`（一般性失败）。
6. 握手阶段的读写总超时为 `handshake_timeout`。
7. 没有用户名密码认证，**默认只监听 127.0.0.1**。把 `listen` 改成 `0.0.0.0` 等于对外开放一个无认证代理（UDP 中继也同样开放，但只接受 SOCKS 控制连接对端 IP 发来的数据报）。

域名**原样**发给服务端（远端解析），不做本地解析，所以没有 DNS 泄露（UDP 也一样）。

## 10. 发送调度与流量整形

> 本章是**发送策略**，不影响互通。参数均来自参考实现。

### 10.1 合并调度器（`merge.go: Box / Gate`）

两个方向各有一个调度器，参数 `Pack`（目标帧大小，`send_pack`）、`Tail`（`send_tail`）、`Quiet`（`send_quiet`，毫秒）。`Box` 是一个字节块队列，`Bundle` 贪心地把队首起连续的块合并成一块，总长不超过 `Pack`，**不拆分块**。

`Feed(src)` 对到来的数据按 `Pack` 切成片放入 Box，然后：

1. **闲时立发（lull）**：若 Box 此前为空，且距上一次 Feed ≥ **40 µs**（`lullGap`），则立即发出。这是交互延迟低的关键。
2. **满则发**：Box 内字节数 ≥ `Pack`，或剩余空间 `Pack − 字节数 < Tail`，立即发出。
3. 否则启动 **250 µs**（`simmerTick`）的定时器；到期时：若已满则发出；若这段时间里**又有新数据到来**且已等待的轮数 < `Quiet × 4`，则继续再等一轮；否则发出。（所以 `send_quiet = 4` 的含义是「只要还有新数据在紧跟着到来，最多持续合并 4 ms」。）

「发出」= 反复 `Bundle` 直到 Box 清空，每次 `Bundle` 产生一个 DATA 帧，由 `emit` 写入隧道（`Tunnel.SendWire / SendWirePad`：长度头直接写进缓冲区预留的 2 字节里，一帧一次 `Write`）。

### 10.2 前几个包的「伪装画像」（persona，`chameleon.go: personaPlan`）

每个会话在每个方向上独立随机抽取一个「计划」：前 N 个包的目标大小 `t`。画像会根据**这个会话承载的流量类型**自适应，输入只有一个布尔提示 `inner`，不依赖任何速率、延迟或丢包测量：

```
inner = 目标端口 ∈ {443, 465, 563, 636, 853, 993, 995, 5223, 8443}   // 内层很可能是 TLS（tlsLike）

N = 2 + rand{0,1,2}              // 下行
N = 2 + rand{0,1,2} + 1          // 上行
inner 时 N += 2；N 至多 8（ShapeSlots）

默认区间  [lo, hi] = 下行 [60, 1400]，上行 [40, 1200]
大包概率  bulky = 5（每个包以 1/5 取大包区间）；inner 时 bulky = 3（1/3）
第 i 个包的区间 [l, h]：
  i = 0 且上行：  [110, 900]
  i = 0 且下行：  [100, 1500]
  其他 i：        以 1/bulky 的概率取 [1400, 4000]；否则 [lo, hi]
t = clamp( 对数均匀抽样(l, h)，24，16382 )
i = 0 且上行：  t = max(t, 首次发送的字节数)   // Proof + Hello 的总长，保证放得下
```

为什么用端口提示：内层是 TLS 的会话，前几个包是内层握手（ClientHello、ServerHello+证书链…），长度分布更偏向大包，覆盖更长的前缀可以让「隧道里的握手形态」更难被辨认。提示错了（非标准端口上的 TLS，或标准端口上的非 TLS）只会让计划稍长或稍短，**不影响正确性**。客户端用 SOCKS 请求里的目标端口，服务端用 Hello 里的端口，两端各自独立计算。

`t` 是**这个包的 body 字节数**（DATA 数据 + PAD，不含 2 字节长度头）。因此 TLS 下这条记录的明文长度为 `t + 2`。

执行（`Gate.shapeDrain`）：把数据积累起来，当积累 ≥ `t` 就切出恰好 `t` 字节发一个包，多余的留给下一个包；若积累不足 `t` 但**填充计时器**（2 ms，`personaFill`；从该包的第一块数据到达时开始计时，之后陆续到达的数据**不会**重置它，所以等待有明确上界）到期，则强制发出，并在 DATA 后面追加 PAD，使 body 总长恰为 `t`（PAD 总开销 `t − n ≥ 4` 才补，否则不补）。所有计划包发完后回到 10.1 的普通合并。

- **服务端首包的特殊处理**：第一个下行 DATA 帧会在数据前加 1 字节 `0x00` 应答码，而计划是按不含应答码的数据算的，所以该帧的 body 比计划多 1 字节。
- **服务端大块直写**（≥ 32766 字节）不走计划，也不填充。
- 计划按会话重新抽取；复用隧道上的新会话照样重新抽。

### 10.3 用户指定整形（`shape_up`）

客户端设置了 `shape_up`（≤ 8 组 `[min, max]`，`1 ≤ min ≤ max ≤ 16382`）时，**取代**客户端上行的自动画像：

- 第 0 组的 `min` 被抬到不小于首次发送的字节数，`max` 抬到不小于 `min`。
- 第 *i* 个包：积累到 ≥ `min[i]` 才发，每包至多 `max[i]` 字节，多余的留给下一包；等待超过 `shape_wait`（默认 20 ms，同样从第一块数据到达时起算、不会被新数据重置）仍不足则按现有数据发出，**不填充**。
- 下行方向仍然使用自动画像。

## 11. 客户端隧道池与拨号策略

> 实现策略，不影响互通。

### 11.1 取用与放回（`purrPool`）

- 池是 LIFO：取最近放回的一条；取出时若已过期（`pool_max_age`）或后台观察者发现对端已关闭，则丢弃并继续取下一条。
- 放回时：若该隧道的使用次数 ≥ `pool_max_uses`（>0 时，硬上限；随机寿命另见第 12 章），或池已满（`pool_hi` 条闲置），或池已关闭，则直接关闭；否则放入并启动后台观察者。
- 每秒一次的清理：丢弃过期或已死的闲置隧道。
- **复用判据**见 6.1。

### 11.2 预连接与池大小

- 维持一个目标值 `want`（初值 `pool_lo`）。每秒调整一次：令 `need = 本秒会话数 + 1`。
  - 本秒有取池失败（miss > 0）：`want += max(miss × 4, 4)`；
  - 否则若 `need > want`：`want = need × 1.5`；
  - 否则连续 10 秒无变化且 `want > pool_lo` 且 `want > 2 × need`：`want −= want / 8`（至少回落到 `pool_lo`）。
  - 最后夹到 `[pool_lo, 当前 poolHi 调谐值]`。
- 后台按需补充：新建数 `n = min(want − 闲置数 − 在途数, 16 − 在途数)`，每个新建任务先随机等待 **0–120 ms** 的抖动再拨号（避免一排握手同时出现），并发上限 16（`spawnCap`）。
- 失败退避：连续失败 `f` 次后，下一次预连接最早在 `500 ms << min(f, 6)` 后（1 s … 32 s）。
- 日志：第一次成功、恢复正常、`fails == 1` 或每 10 次失败时输出。

### 11.3 在线调谐（每 3 秒）

三档调谐：

| 档位 | `poolHi` | `raceN` |
|---|---|---|
| fast | `pool_hi + 64` | 10 |
| mid | `pool_hi` | `race_count` |
| slow | `pool_lo + 8` | 3 |

选择：连续失败 ≥ 3 → fast；样本数 < 8 → mid；命中率 < 0.5 → fast；失败为 0 且命中率 > 0.9 且 平均握手 RTT < 300 ms → slow；否则 mid。命中率是进程**累计**的（取池成功 / 总次数，不清零）。每次只向目标档位移动 1/3 的差距（至少 1），并夹到 `poolHi ∈ [pool_lo+4, max(pool_hi,128)]`、`raceN ∈ [2,12]`。

### 11.4 取不到热隧道时：赛跑拨号（`scout.race`）

1. 候选地址 = 所有 `server` 条目解析出的全部 IP（DNS 缓存 30 s），IPv4/IPv6 交错，**先随机洗牌**，再按成本**稳定排序**；成本 = 该地址握手延迟的指数滑动平均（新值权重 1/4）；从未测过的为 100 ms；失败过的在冷却期内加 2 s，冷却时长 `min(失败次数 × 2 s, 60 s)`，失败时延迟估计翻倍 + 1 s（上限 30 s）；地址簿至多 4096 项。
2. 取前 `raceN` 个。第 0、1 个**立即**开始，第 *i*（i ≥ 2）个延迟 `(i−1) × 50 ms`。
3. 第一个握手完成者胜出并返回；落选者在后台完成握手后**加入池**（不浪费），其余取消。

## 12. 自适应整形与隧道寿命

> 实现策略，不影响互通。`chameleon.go: personaPlan / lifespan`。
>
> **设计原则**：不测速、不判断「变慢」。线路抖动、拥塞、对端负载都会让速率下降，要可靠地区分它们与限速需要大量判断，代价是性能与误判，所以参考实现**没有任何基于速率、延迟或丢包反馈的控制器**。自适应只体现在两处：**按流量类型调整整形**（10.2）与**每条隧道随机寿命**（本章）。两者都是前馈的，输入只有目标端口和随机数。

### 12.1 每条隧道的随机寿命

隧道第一次被客户端用于会话时（`Kitten.fresh`）抽取一个寿命 `life = (uses, bytes)`，之后不再改变：

```
bytes = 对数均匀抽样(8 MiB, 256 MiB)
uses  = 0                                           若 pool_max_uses = 0（不限）
uses  = lowest + rand[0, max − lowest]              否则，max = pool_max_uses，lowest = ceil(max / 2) = (max + 1) / 2
```

`spent(uses, moved)` = `(uses > 0 且 已用会话数 ≥ uses)` 或 `(moved ≥ bytes)`；`moved` 是 `Tunnel.Moved`（两个方向的帧头、数据与 PAD 的总和）。会话结束时 `spent` 为真，则隧道不放回池中而被关闭（`release` 的最后一项判据）。

目的：让「一条隧道承载多少个会话、搬运多少字节后退役」在不同隧道之间互不相同，没有固定的边界可以统计；同时也自然限制任何单条隧道上累计的流量。池的硬上限 `pool_max_uses` 仍然生效（`purrPool.put`）。

### 12.2 与旧版本的差异（实现者注意）

早期草案里有一个「自适应对抗控制器」（观测下行速率、判定限速、收紧字节预算与复用次数）。**它已被删除**，规范不再包含它，客户端不得依赖。删除后行为变化：没有速率观测；没有 `heat` 档位；整形画像不再随警戒档位变宽；握手连续失败不再触发任何整形变化（只输出日志）。

## 15. 安全考虑与已知边界

这一章是写给要在这个协议上做决策的人的，请认真读。

**已有的保护**

- 防重放（nonce 缓存 + 启动检查 + 时间窗）、防跨会话转发（TLS exporter 绑定）、常量时间比较、缓存满时拒绝；
- 认证失败不沉默，伪装成普通站点（诱饵）；
- 默认不允许出站到私网/回环/链路本地；
- 首包大小随机、整形计划随机（并按目标端口调整覆盖长度）、隧道寿命随机、探测者看到 `http/1.1` 的 ALPN；
- 会话之间的 NAP 交换与残留检查（6.1、6.2）；
- UDP 出站同样受私网拦截约束，服务端的 UDP 套接字只接受「自己发过包的 IP」的回包（17.5）。

**已知边界（没有处理，或只部分处理）**

1. **NAP 是一个未填充的、孤立的 2 字节帧**：TLS 1.3 下表现为一条 24 字节的记录（5 + 2 + 1 + 16），出现在每个会话结束时（双向各一条）。这是一个可以被统计的「会话边界」特征。参考实现 v1 没有对它做填充或延迟。
2. **Hello 里没有长度混淆**；`Cozy`-only 帧（目标无数据直接结束）为 1 字节 DATA。
3. **TLS ClientHello 指纹仍是 Go 标准库的**（扩展顺序、密码套件列表固定）；ALPN 与 TLS 1.2/1.3 版本范围只做到了「看起来像浏览器」的一部分。
4. **诱饵不是完美的 nginx**：没有 `ETag`、`Last-Modified`、`Server` 版本号、`Accept-Ranges` 等头；不完整请求头的等待时间是 1 秒（真实 nginx 默认 60 秒）；TLS 下的非 TLS 流量由 Go 的 TLS 库按其默认行为处理（直接关闭），不会回应 HTTP 页面。
5. **预认证资源占用**：TLS 握手完成（或明文连接建立）后，服务端会等待首帧最长 `idle_timeout`（默认 2 分钟）；这段时间内连接占用一个 `max_conns` 槽位。攻击者可以用大量慢连接占满槽位。生产环境请配合防火墙/限速，或调小 `idle_timeout`。
6. **uuid 即全部凭据**；明文模式没有保密性与服务端身份认证。
7. **时钟**：两端时钟差超过 30 秒所有握手都会失败。
8. **指纹固定**模式下不检查证书有效期和域名；换证书需要同步更新所有客户端的 pin。
9. **隧道内是 TLS 时的内层握手形态**（TLS-in-TLS）依然可能被基于包长序列的方法识别，整形只覆盖每个方向的前几个包。
10. **没有针对限速的反馈控制**：整形与隧道寿命都是前馈随机化（第 12 章），不会因为「变慢」而改变行为，所以也不会被线路抖动误导；代价是它对已经发生的限速不会做任何补救，也无法把正在进行的会话迁移到新隧道。
11. **会话隔离靠顺序与 NAP，没有会话编号**（6.2）；已认证的对端（或明文模式下的路径攻击者）在下一个 Hello 之后注入字节无法被检测。
12. **内层 TLS 提示只看目标端口**，不检查实际内容。
13. **UoT 只做时序扰动，不做大小隐藏**：数据报长度原样出现在记录里（只被合并写入模糊了边界），固定码率的语音流仍然有稳定的包长特征；首帧和应答帧有随机填充，但它们之后的帧没有（17.4）。
14. **UoT 的 TCP 头阻塞**：隧道是一条可靠有序的 TCP 连接，丢包重传期间该关联上的所有数据报一起被延迟。对语音这是延迟抖动而不是丢字；对自带重传 / 拥塞控制的上层协议（QUIC、KCP 等）可能出现双重重传，吞吐会比直连差。
15. **半关闭超时是资源保留时间**：目标无视 FIN 又一直沉默时，服务端会在这个连接和一条隧道槽位上多停留 `half_close_timeout`（默认 2 分钟）；调小可以更快回收，但会截断真的需要长时间沉默后才响应的半关闭请求。

## 16. 分享链接与订阅格式（客户端集成）

> 本章是**客户端 / 配置交换的互操作格式**，不是线上协议。图形客户端用它导入节点，服务端脚本用它输出节点。参考实现：`link.go`（`FormatLink` / `ParseLink` / `ParseSubscription` / `EncodeSubscription`），命令行：`nakis link`、`nakis sub`、`nakis client -l`。

### 16.1 分享链接

```
link     = "nakis://" uuid "@" hostport [ "?" query ] [ "#" name ]
hostport = host ":" port            ; IPv6 字面量必须带方括号：[2001:db8::1]:443
query    = key "=" value *( "&" key "=" value )
name     = 节点名，UTF-8，百分号编码（空格 → %20，不要用 +）
```

- 方案名大小写不敏感（解析时），生成时一律小写 `nakis://`。
- `uuid`：32 位十六进制，带不带连字符都接受，大小写不限；生成时为小写 `8-4-4-4-12`。**uuid 就是凭据**（等同密码），链接与订阅必须按机密对待。
- `host`：域名或 IP；`port`：1–65535。这是**主服务器**。
- `query` 里的值按标准 URL 查询字符串规则解码（百分号解码；注意 `+` 会被解成空格，所以 base64 值要么用 base64url，要么把 `+` 编成 `%2B`；参考实现解析 `ech` 时会把空格还原成 `+`）。生成端不会额外编码 `,` `:` `[` `]`。
- **只写与默认值不同的参数**；`v` 总是写。**未知参数必须忽略**（所以以后可以增加可选参数而不升版本）；同名参数出现多次时取**第一个**；参数顺序无意义。

| 参数 | 值 | 默认 | 对应 `client.json` 字段 / 含义 |
|---|---|---|---|
| `v` | 整数 | 1 | 链接格式版本。缺省按 1；大于实现所懂的版本 → **整条链接作废**（拒绝导入） |
| `tls` | `0` | TLS 开 | 只有值 `0` 有意义，表示明文（`tls=false`）；明文与 `pin` / `ech` 互斥（出现则无效） |
| `sni` | 主机名 | 空 | `sni`：TLS 的服务器名；开 ECH 时是内层真实名字。TLS 下 `sni` 与 `pin` **至少有一个**，`ech` 必须有 `sni` |
| `pin` | 64 位十六进制，逗号分隔多个 | 空 | `tls_pins`：服务端叶子证书 SubjectPublicKeyInfo 的 SHA-256；大小写不限，可含 `:`；有 pin 时不做 CA 校验（2.2） |
| `ech` | base64 | 空 | `ech_config`：**ECHConfigList**（含 2 字节总长度前缀，见 2.3）；base64 标准或 URL 安全字母表均可，填充可有可无；解码后至少 4 字节。输出用 URL 安全字母表、无填充 |
| `alt` | `host:port` 逗号分隔 | 空 | 额外服务器：追加在主服务器之后，构成 `server` 的逗号列表（赛跑候选，11.4）；IPv6 同样要方括号 |
| `shape` | `lo-hi` 逗号分隔，至多 8 段 | 空 | `shape_up`：`1 ≤ lo ≤ hi ≤ 16382`（10.3） |
| `race` | 整数 | 3 | `race_count`，夹到 [2, 12] |
| `pool` | `lo-hi` | `2-32` | `pool_lo` / `pool_hi`（lo 夹到 [1, 1024]，hi 夹到 [lo+1, 4096]） |
| `uses` | 整数 | 8 | `pool_max_uses`，夹到 [0, 100]（0 = 不限） |
| `age` | 时长 | `45s` | `pool_max_age` |
| `ka` | 时长 | `15s` | `keepalive` |
| `wait` | 时长 | `20ms` | `shape_wait` |
| `cc` | 算法名 | 空 | `congestion`（仅 Linux 有效，其他平台忽略） |
| `pack` | 整数 | 20480 | `send_pack`，夹到 [1024, 65533] |
| `tail` | 整数 | 512 | `send_tail`，夹到 [0, pack−1] |
| `quiet` | 整数 | 4 | `send_quiet`，夹到 [0, 64] |

时长用 Go 语法：`500ms`、`45s`、`2m`、`1h`。数值越界时**不报错而是夹到范围内**，非数字或非法格式则整条链接无效。**不在链接里的东西**：本地监听地址（`listen`）、日志级别——由客户端自己决定（`nakis client -l LINK` 默认监听 `127.0.0.1:1080`，用 `-listen` 覆盖）。

**校验顺序**（任一失败 → 这条链接无效，不得部分导入）：方案 → uuid → host/port → `v` → 各参数格式 → 组合约束（TLS 下 `sni`/`pin` 至少一个；`ech` 需要 `sni`；明文不得带 `pin`/`ech`）。

### 16.2 订阅

订阅是一个文本：

1. 先判断：去掉首尾空白与 UTF-8 BOM 后，若文本里**不含** `nakis://`（不区分大小写），则把它当作 **base64**（标准或 URL 安全字母表、有无填充均可，忽略所有空白与换行）解码一次，得到明文；否则直接当明文。
2. 明文按行拆分（`\n` 或 `\r\n`），空行与以 `#` 开头的行忽略；**不是 `nakis://` 开头的行忽略**（这样订阅里可以混有别的协议的链接）；其余每行是一个分享链接。
3. 某一行无效**只跳过那一行**，其他节点照常导入，并应向用户报告被跳过的行号与原因。全部无效 → 导入失败。
4. 节点顺序按出现顺序；节点名取各链接的 `#name`（可为空，客户端自行命名）。

参考实现生成订阅（`EncodeSubscription`）：链接用 `\n` 连接并以换行结尾，整体做**标准 base64（带填充，不换行）**。

服务端不提供订阅的 HTTP 服务；把订阅文本放到任意静态网址即可（**必须用 HTTPS**，内容含 uuid）。托管方如果能设置响应头，客户端通常会识别这些**约定俗成**的头（不属于本规范，缺省不影响导入）：`Profile-Update-Interval`（小时）、`Profile-Title`、`Subscription-Userinfo`。

### 16.3 从服务端配置生成链接（`nakis link -s`）

`LinkFromServer` 的规则，生成端实现者需要一致：

- `host`：用户指定的对外地址；`port`：`-port`，缺省取 `listen` 的端口；`uuid` 取自服务端配置。
- `tls`：`true` 时带证书指纹：读取 `tls_cert` 的**第一个 PEM 块**，按 2.2 计算 SPKI 的 SHA-256 作为 `pin`；使用 CA 签发、会续期的证书时应加 `-nopin` 去掉 `pin`（否则续期后指纹变化会让所有客户端失效），此时 `sni` 必须是证书的域名。
- `ech`：取 `ech_keys[0].config`（单个 ECHConfig 的 base64），**前面加 2 字节大端长度**得到 ECHConfigList，再按 16.1 编码；此时必须有 `sni`。
- `sni`：`-sni` 或（`host` 是域名时）`host`。

## 17. UDP over TCP（UoT）

SOCKS5 应用要发 UDP（语音通话、QUIC、DNS、游戏）时，客户端自动把它走进一条隧道，TCP 请求完全按原有逻辑，互不影响。这一章是 UoT 的完整定义。

### 17.1 触发与魔术地址

应用发起 SOCKS5 `UDP ASSOCIATE`（9）时，客户端从隧道池取一条隧道（与 TCP 会话共用同一个池和同一套拨号、赛跑、复用逻辑），发出一个普通的 Hello（第 5.1 节），目标是魔术地址：

```
host = "udp.nakis.arpa"（14 字节）  port = 0
hello = 01 01 00 0e 75 64 70 2e 6e 61 6b 69 73 2e 61 72 70 61 00 00
```

服务端在读完 Hello 之后、拨号之前检查 `host`，命中就进入 UoT；没有新的命令字节，线上字节格式不变，所以对不认识 UoT 的老服务端，它只是一个解析不了的域名（拨号失败 → Oops → 客户端关联结束）。Proof 与 TCP 会话完全一样，没有任何额外认证。

选魔术地址而不是新命令字节，是为了让线上只有一种 Hello，也便于后续加别的旁路。`.arpa` 是保留的基础设施域，不会和真实目标冲突。

### 17.2 应答与首帧

- 客户端首帧：`[Proof][Hello]` 后面紧跟一个 PAD 帧（第 3 章，总开销 **4～403 字节**、内容随机，同一次写入发出）。UoT 不使用 TCP 路径的首包整形计划，也没有应用数据跟在首帧里。
- 服务端应答：`0x00`（Cozy）后面同样紧跟一个总开销 4～403 字节的 PAD 帧，**立即**发出（TCP 会话里应答要等第一批下行数据，UoT 不等）。失败时发 Oops 后关闭隧道：UDP 被服务端关闭（`udp = false`）、打不开 UDP 套接字。
- 客户端在隧道就绪、首帧发出之后才回复 SOCKS 成功。

### 17.3 数据报记录

应答之后，两个方向的字节流都是一串**记录**（流内的帧边界没有意义，记录自己带长度）：

```
record = atyp(1)  addr  port(2)  len(2)  data(len)
atyp   = 1 : addr = 4 字节 IPv4
         3 : addr = len(1) + 域名（1～255 字节）
         4 : addr = 16 字节 IPv6
```

- 上行（客户端 → 服务端）：`addr:port` 是数据报的**目的地**。域名原样发给服务端，由服务端解析。
- 下行（服务端 → 客户端）：`addr:port` 是数据报的**来源**（总是 IP 字面量）。
- `len` 至多 65535，参考实现不分片也不重组；`port = 0` 的上行记录被丢弃；记录被 NAP 或 EOF 截断算协议错误，隧道关闭。

### 17.4 mux：只做时序扰动

记录交给一个极简的 mux 再写入隧道（`udp.go: jitterMux`，两端各一个，各管一个方向）。它不是为性能设计的，唯一目的是打散「一个数据报对应一次发送」的时序：

1. 所有记录进同一个先进先出队列，由**一个**发送协程取走，所以顺序保持。
2. 队列从空变成非空后，发送协程先睡一个**均匀随机**的时间，范围 `(0, udp_jitter]`（默认 8 ms，上限钳到 200 ms，`0` 表示关闭），睡醒后把队列里现有的记录**合并**成至多 32 KiB 一次写出（超过则连续再写，不再睡）。
3. 队列总量上限 1 MiB，满了丢弃**新**到的记录（UDP 本来就允许丢）；发送失败则放弃整个队列并让关联结束。
4. 睡眠期间到达的记录会和第一个一起发出，所以一个 20 ms 一包的语音流，到达对端的间隔不再是稳定的 20 ms，有时会被并在一起。

没有做的：不改变记录长度（见第 15 章第 13 条），不制造假流量，不在空闲时发送任何东西。语音可以承受的额外时延是个位数毫秒到十几毫秒，所以默认值只取 8 ms，平均额外延迟约 4 ms。

### 17.5 服务端行为

每个关联一个 UDP 套接字（`net.ListenPacket("udp", ":0")`，系统分配端口，双栈）：

- **目的地解析**：IP 字面量直接用；域名走与 TCP 相同的 DNS 缓存（8.1），超时用 `dial_timeout`，多个结果取第一个 IPv4（没有则第一个 IPv6），结果在该关联内缓存（至多 256 个名字，满了清空）。
- **私网拦截**：`allow_private = false` 时，目的 IP 命中 8.2 的任何一类就丢弃该数据报（只写 Debug 日志，不通知客户端）。
- **回包过滤**：套接字只接受来源 **IP** 在「该关联发过包的目的 IP 集合」里的数据报（地址受限锥形，不限端口，方便 WebRTC 一类从同一主机的其他端口回包的场景），集合至多 4096 项，满了淘汰最早的。其余数据报静默丢弃，所以别人扫到这个端口也灌不进数据。
- **空闲回收**：`udp_idle_timeout`（默认 5 分钟）内两个方向都没有数据报，服务端直接关闭隧道（不发 NAP，不复用）；检查周期 10 秒。
- 套接字读取连续失败 50 次则关闭关联；服务端退出时立即结束所有关联。

### 17.6 客户端行为（SOCKS5 UDP ASSOCIATE）

- 中继套接字绑定在 SOCKS TCP 连接的**本地 IP** 上、端口由系统分配；回复里的 `BND.ADDR:BND.PORT` 就是它，应用把带 SOCKS5 UDP 头（`RSV(2) FRAG(1) ATYP ADDR PORT DATA`）的数据报发到这里。
- 只接受来源 IP 等于 SOCKS 控制连接对端 IP 的数据报；来源端口锁定为第一个有效数据报的端口（若请求里给了非 0 的 `DST.PORT` 且 `DST.ADDR` 不是未指定地址，则必须是它）；其他来源静默丢弃。`FRAG != 0` 的数据报丢弃（不做分片重组）。目的是魔术地址的丢弃。
- 下行：给每个记录加上 SOCKS5 UDP 头（来源为记录里的地址）后发回应用的那个来源地址。
- **关联的生命周期等于 SOCKS 控制连接**（RFC 1928）：控制连接关闭、隧道出错、服务端 NAP、客户端 `Shutdown` 任一发生，关联就结束。

### 17.7 结束与复用

结束流程和 TCP 会话一样用 NAP 交换（5.4）：

1. 一方先结束：先把 mux 里剩下的记录发完，再发 NAP。
2. 另一方读到 NAP（此时记录流恰好停在记录边界上，否则算协议错误）后关闭 UDP 套接字、发完剩余记录，回自己的 NAP。
3. 客户端发出 NAP 后用排空窗口（5.4 客户端第 3 条）等服务端的 NAP；双方 NAP 都交换成功且接收缓冲干净，隧道回到池里复用，与 TCP 会话用同一套判据（6.1），寿命计数也一并计入。

UDP 关联期间，这条隧道不能同时承载 TCP 会话（一条隧道同一时刻只有一个会话）。
