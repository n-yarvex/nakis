## 2. 测试环境与方法

**机器**：Go 1.24.7、linux/amd64、2 vCPU（Intel Xeon @ 2.10 GHz）、共享虚拟机。客户端、服务端、目标服务、测试程序全部在同一台机器上，通过回环网卡通信。这台机器的速度会随时间浮动（同一份测试不同次相差 ±15% 很正常），所以**请把数字当比例看，只在同一张表里横向比较**。

**测试台（rig）**：在进程内启动一个**真实的**客户端（SOCKS5 入口）和一个**真实的**服务端，中间可以按需插入：

- **三种模式**：`plain`（明文）、`tls`（TLS 1.3 + 指纹固定）、`tls+ech`（TLS 1.3 + ECH）；
- **延迟线 WAN**：给两个方向各加固定的单程延迟（本报告用 40 ms，即 RTT 80 ms）。**只模拟延迟，不模拟丢包与带宽限制**；
- **中间盒（middlebox）**：一个在客户端和服务端之间的 TCP 代理，逐流记录抓到的字节，并可以挂一个「判决函数」去**限速**它认为可疑的流（用来模拟运营商的识别与限速）；
- **目标服务**：回显服务、固定字节数的批量发送/接收服务。

**重要说明**：「分类器」「限速器」都是**作者自己写的模拟器**，判据是作者假设的（例如「首个应用数据记录 ≤ 120 字节」「单流超过 1.5 MB 后限到 300 KB/s」），**不是任何真实运营商的实际规则**。它们能证明的是：机制按设计工作；证明不了的是：真实运营商一定这样做。

## 3. 吞吐

**方法**：经 SOCKS5 建一个会话，通过 nakis 隧道单向传输 64 MiB（下载 = 目标 → 应用，上传 = 应用 → 目标），三轮取范围。本轮实测，Go benchmark `BenchmarkTunnel`。

| 模式 | 下载 | 上传 |
|---|---|---|
| 明文 | 1170–1310 MB/s | 1300–1420 MB/s |
| TLS 1.3 | 680–740 MB/s | 840–1010 MB/s |
| TLS 1.3 + ECH | 650–730 MB/s | 1010–1065 MB/s |

解读：

- 回环、2 核，两端的加解密与拷贝挤在同样的两个核上，所以这里测的是**每字节的 CPU 成本**，真实链路上瓶颈通常是带宽，不是这里的数字。
- TLS 大约吃掉一半的下载吞吐（推测是两端的加解密挤在同样两个核上，没有单独做性能剖析）；ECH 只改变握手，不改变每字节开销，所以与普通 TLS 持平。
- 上一版 README 记录的另一轮测量里明文下载曾到 1380–1550 MB/s，反映的就是机器自身的浮动。

**逐帧发送的微基准**（`BenchmarkSend`，单个帧写入的吞吐，三轮范围，MB/s）：

| 帧大小 | 明文 | TLS（带记录批量器） | TLS（不带批量器） |
|---|---|---|---|
| 512 B | 139–160 | 106–136 | 113–137 |
| 4096 B | 1055–1382 | 834–933 | 867–1006 |
| 16000 B | 2326–2796 | 1298–1968 | 1463–1954 |
| 60000 B | 3887–4973 | 1727–1879 | 1475–1934 |

> **诚实说明**：TLS 记录批量器（把超过 16384 字节的大帧拆出的多条 TLS 记录合并成一次系统调用）在这台机器的回环测试里，**与不带批量器的结果在噪声范围内重叠，没有测出显著的吞吐收益**。它的设计目的是在真实网络上减少大帧产生的小报文数与系统调用，这一点本测试没有证明，请不要把它当作已被证实的优势。

## 4. 交互延迟

**方法**：经隧道做 64 字节的一问一答（ping-pong），测 1000 轮的 p50 / p99，回环无延迟线。`LAT` 用例。

| 模式 | p50 | p99 | 本轮（`-race`，更慢） |
|---|---|---|---|
| 明文 | 70 µs | 1.26 ms | 90 µs / 200 µs |
| TLS | 60 µs | 1.26 ms | 120 µs / 240 µs |
| TLS + ECH | 60 µs | 1.22 ms | 130 µs / 280 µs |

- 优化前（早先实测，同一用例的旧版本）：**约 11.7 ms**——小包要等一个合并窗口，两个方向各等一次。
- 现在：队列为空且距离上一次数据已经过去 ≥ 40 µs 的小包**立即发走**，只有紧跟着到达的包才合并，所以交互场景下的延迟下降了两个数量级以上。
- p99 在 1.2 ms 左右，推测与系统定时器粒度/调度抖动有关（紧挨着到达的两个包会等一个 250 µs 的合并拍），没有单独验证。
- `-race` 模式下检测器本身有开销，数字更大，放在最后一列只是说明「开着竞态检测也跑得过」。

## 5. 小包合并

**方法**：应用连续写 4000 次、每次 150 字节（共 600 KB），数服务端实际收到多少个上行帧。`MERGE` 用例。

| 运行 | 上行帧数 | 平均每帧 |
|---|---|---|
| 本轮（正常） | **36** | 16.7 KB |
| 本轮（`-race`） | 54 | 11.1 KB |
| 早先实测 | 35 | ≈17 KB |

也就是 **4000 次小写入被合并成几十个帧**（约 110×），延迟优化（闲时立发）没有破坏合并。

## 6. 往返次数（RTT）

**方法**：给隧道加单程 40 ms 的延迟线（RTT = 80 ms），测**从应用写出第一个字节，到收到回显的第一个字节**所用时间，折算成 RTT 的倍数。计时从 SOCKS5 成功回应之后才开始（那时拨号已在路上），所以冷启动会略低于「握手 + 请求」的理论值。

| 场景 | 明文 | TLS | TLS + ECH |
|---|---|---|---|
| **热**（池里有预先建好的隧道） | 86 ms = **1.1 RTT** | 86 ms = **1.1 RTT** | 86 ms = **1.1 RTT** |
| **冷**（现场建连接） | 124 ms = **1.6 RTT** | 209 ms = **2.6 RTT** | 209 ms = **2.6 RTT** |

- 热路径与握手方式无关：认证证明和请求被塞进同一个帧里发出，**没有额外的确认往返**。理论下限是 1 RTT，实测 1.1。
- 冷启动的 TLS 需要一次 TCP 握手（1 RTT）加 TLS 1.3 握手（1 RTT）再加请求/响应（1 RTT），实测 2.6 RTT 是因为计时起点在 SOCKS 回应之后（TCP 握手已部分完成）。
- 这就是 nakis 要把**预连接**做成永远开启的原因：热路径把 TLS 的 2 个往返完全藏在了用户看不见的地方。

## 7. 抗特征识别：首包随机化

**动机**：旧版客户端在 TLS 握手后的第一条记录永远是一个固定大小的小记录（只装认证证明），服务端第一次回应也是固定的极小包，所有隧道前几个包的大小序列一模一样——这是最容易被统计出来的特征。现在把认证证明并进首帧，并为每条隧道随机抽取「前 2–5 个包」的大小（对数均匀分布）。

**方法**：新建 80 条隧道（每条只发一个会话，强制不复用），统计抓到的第一个包大小。两轮独立运行：

| 度量 | 客户端首包（明文） | 服务端首包（明文） | 客户端首包（TLS） |
|---|---|---|---|
| 不同大小的种数（共 80 条） | 74–79 | 74–79 | 74–77 |
| 出现最多的大小所占比例 | 2% | 2% | 2% |
| 最小首包 | 112 B | 102–106 B | 129–136 B |
| 平均首包 | 369–399 B | 542–575 B | 386–460 B |

解读：几乎每条隧道的首包大小都不同，没有任何一个大小占比超过 2%（80 条里最多出现 1–2 次）。代价是每个新会话的前几个包平均多传不到 1 KB 的填充。

> 注意：这些大小范围是**作者选定**的（几十字节到几 KB、对数均匀），**不是**从真实 HTTPS 流量里测出来的分布。它证明的是「没有固定的首包大小特征」，不证明「与某种真实应用无法区分」。

## 8. 抗限速：特征分类器对照与单流限速学习

### 8.1 「首包很小就限速」的分类器

**方法**：在中间盒里放一个判决函数，模拟一种假想的运营商策略——**如果一个流的第一个应用数据记录 ≤ 120 字节，就把它限速到 100 KB/s**。对照组把客户端的整形强制设成「最小的首包」（这正是旧版的特征）；实验组用默认配置。各跑 6 个新隧道，每个回显 120 KB。

| 组 | 被限速的隧道 | 6 × 120 KB 回显总耗时（两轮） |
|---|---|---|
| 对照：首包极小（旧特征） | **6 / 6** | 9.26 s、9.44 s |
| 默认首包 | **0 / 6** | 90 ms、10 ms |

结论：这个假想分类器能抓住旧特征（证明它确实在工作），而默认配置完全不会被它命中，速度差 100 倍以上。

### 8.2 「单流超量限速」与自适应学习

**方法**：中间盒在**一条流**累计传输超过约 1.5 MB 后把它限速到 300 KB/s（模拟运营商对长连接/大流量单流降速）。客户端连续发起 8 个会话，每个会话回显 400 KB（一条隧道每个会话来回约 800 KB）。对比「关闭学习」与「开启学习」。

两轮实测（每个数字是一个会话的耗时）：

| 组 | 第 1 轮 | 第 2 轮 | 慢会话数 |
|---|---|---|---|
| 不学习 | 50 ms, 420 ms, 1.5 s, 1.49 s, 1.5 s, 1.5 s, 1.48 s, 1.49 s | 10 ms, 420 ms, 1.47 s, 1.48 s, 1.47 s, 1.48 s, 1.47 s, 1.48 s | **6** |
| 学习 | 40 ms, 420 ms, **1.49 s**, 30 ms, 420 ms, 40 ms, 400 ms, 30 ms | 0, 390 ms, **1.48 s**, 0, 0, 0, 0, 0 | **1** |

解读：学习版只在第 3 个会话撞上限速（1 次，不可避免——必须先被限一次才能学到），随后控制器把每条隧道的字节预算压到学到的阈值以下并更频繁地换新隧道，**之后的会话全部恢复到几十毫秒**；不学习版在第 3 个会话之后每一个都被拖慢到约 1.5 秒。

> 这只证明「控制器在这类单流限速模型里能学会并规避」。**不能**外推到：基于目标 IP、端口、整体加密流量的限速；以及对**正在进行中的那一个会话**的保护（它仍会变慢，见 §15）。

## 9. 抗主动探测：诱饵实测

**方法**：对**真实二进制**（明文模式的 `nakis server`，监听回环）用 Python 套接字发送各种探测，记录响应与耗时。本轮实测。

| 探测 | 响应 | 耗时 |
|---|---|---|
| `GET / HTTP/1.1` + `Host` + 空行 | `200 OK`，nginx 欢迎页（751 字节含头） | 立即 |
| `GET /admin HTTP/1.1` … | `404 Not Found`，nginx 风格（289 字节） | 立即 |
| `HEAD / HTTP/1.1` … | `200 OK`，只有头（136 字节） | 立即 |
| 随机字节 + `\r\n\r\n` | `400 Bad Request` | 立即 |
| 5000 字节无换行乱码 | `400 Bad Request` | 立即 |
| 40 字节无换行乱码 | 无响应，关闭 | 1.00 s |
| 请求行完整但缺少最后的空行 | 无响应，关闭 | 1.00 s |
| 形状合法但认证错误的 nakis 首帧（71 字节随机内容） | 无响应，关闭 | 1.00 s |
| 长度头声明 64 字节但只发 10 字节 | 无响应，关闭 | 4.00 s |

另有自动化用例确认：

- 明文与 TLS 两种模式下，`GET /` → 200、`GET /admin` → 404、随机乱码 → 400；TLS 下协商出的 ALPN 为 `http/1.1`；
- 客户端发出的 ALPN 列表为 `h2, http/1.1`（浏览器式）；
- 早先实测：对真实二进制（TLS 模式、使用样例配置）用真实的 `curl -k https://服务器/` 访问，得到 nginx 欢迎页。

**这一节的结论与边界**：完整的 HTTP 探测会立即得到像 nginx 的回应；不完整的探测会被静默关闭，而**真实 nginx 对不完整的请求头会等待 60 秒**，所以「等多久」是可被区分的差异。此外诱饵页缺少真实 nginx 的 `ETag`、`Last-Modified`、版本号等头。详见 SPEC §15。

## 10. 认证与重放

全部为自动化用例（本轮 `-race` 实测通过）：

| 检查 | 结果 |
|---|---|
| 同一份证明提交两次 | 第一次通过，第二次被拒（nonce 重放） |
| 重放一段**抓到的完整合法流量**（明文模式，原样重新发到服务端） | 服务端不提供任何隧道服务（2 秒内读到 0 字节） |
| 用错误的 uuid 发起会话（明文、TLS 各一遍） | 拿不到任何数据（连接被静默关闭，客户端日志提示 uuid 或时钟问题） |
| 篡改证明内容 | 被拒 |
| 绑定值不一致（把一条 TLS 会话上的证明转发到另一条） | 被拒 |
| 时间戳超出 ±30 秒 | 被拒（并带偏差值） |
| 时间戳早于服务端启动时刻 | 被拒（重启后旧证明不能被重放） |
| 指向回环/私网的目标（默认配置） | 被服务端拒绝，客户端收到 Oops |
| 错误的 pin | 客户端握手失败，连不上 |
| 服务端没配 ECH 私钥而客户端使用 ECH | 握手失败 |
| 正确的 ECH 配置 | 握手成功 |

**可独立复核的测试向量**：协议规范 SPEC §16.1 给出了一组固定输入下的 HMAC 结果，已用 Go 参考实现和独立的 Python `hmac` 分别计算，两者逐字节一致。

## 11. 正确性与稳定性

下列用例在 `plain` / `tls` / `tls+ech` 三种模式下**全部各跑一遍**（单项耗时为本轮 `-race` 下的数字）：

| 检查 | 内容 | 结果 |
|---|---|---|
| 回显完整性 | 随机数据经隧道回显，逐字节比对 | 通过（0.14 / 0.24 / 0.18 s） |
| 小包风暴 | 大量极小的写入，数据不丢不乱序 | 通过 |
| 客户端先关闭后的复用 | 会话结束后隧道回池，下一个会话继续使用 | 通过 |
| 目标先关闭后的复用 | 同上，由目标一侧结束 | 通过 |
| 拨号失败的干净处理 | 目标不可达时，客户端干净地失败 | 通过 |
| 预连接 | 池按配置预热，首个会话直接用热隧道 | 通过 |
| 整形上行记录大小 | 设置 `shape_up` 后抓包，每条 TLS 记录大小与计划一致（TLS 与 TLS+ECH） | 通过 |

其他稳定性与压力用例：

| 用例 | 结果 |
|---|---|
| **150 个并发会话**，每个 20 KB，逐字节校验 | 全部完整：明文 100–200 ms、TLS 90–690 ms、ECH 130–720 ms（不同轮次，`-race` 下较慢） |

## 13. 真实二进制冒烟与抓包

**方法**：用编译出的真实二进制启动服务端（明文，`allow_private: true`）和客户端（`pool_lo: 1`），中间放一个转发抓包的 TCP 代理，经 SOCKS5 向一个回显服务先后发 `hello nakis` 和 `second session`。本轮实测。

结果（解析后的帧，PAD 为随机填充）：

```
客户端 → 服务端  132 B  DATA(82 B = 认证 56 + Hello 15 + 应用 11) + PAD(48 B)
客户端 → 服务端    2 B  NAP
服务端 → 客户端  844 B  DATA(12 B = 0x00 + 回显 11) + PAD(830 B)
服务端 → 客户端    2 B  NAP
——— 同一条 TCP 连接上的第二个会话 ———
客户端 → 服务端  518 B  DATA(29 B = Hello 15 + 应用 14) + PAD(487 B)
…
```

证实了：认证、请求、应用数据**同一次写入**发出，没有额外往返；两个会话在**同一条隧道**上复用，第二个会话没有认证；两个会话的包大小不同（随机计划）。完整的帧级解析与逐字节说明见 SPEC §16.3。

早先实测：用样例配置（TLS + `shape_up`）启动真实二进制，经 SOCKS5 访问回显，正常。

## 15. 没有测到的东西（请务必读）

下面这些**没有**测过，或者测不了，请不要把本报告当成它们的证明：

1. **真实互联网与真实运营商**：所有「抗限速」结果都来自作者写的模拟器，判据是假设的。真实运营商的识别与限速规则未知、会变，nakis 不能保证任何情况下都不被限速。
2. **丢包、抖动、带宽受限链路**：延迟线只加固定延迟；没有模拟丢包与限带宽，所以 `congestion`（BBR 等）的效果**完全没有测过**。
3. **TLS 指纹（JA3/JA4）**：客户端握手使用 Go 标准库，ClientHello 指纹仍是 Go 的；没有做指纹对比，也没有用 uTLS 之类的库伪装。
4. **与其他协议的对比**：没有与 Shadowsocks、Trojan、VLESS、Snell、AnyTLS 等做过对比测试，所以本报告**没有**任何「比谁快」的结论。想比较请在你自己的链路上用同样的流量亲自测。
5. **Windows / macOS 的运行**：只做了编译与 `go vet`，没有在这两个平台上实际运行。
6. **长时间稳定性**：最长的单项测试是几十秒级；没有做过数小时的浸泡测试，也没有测量长期内存增长。
7. **大规模并发**：并发测试到 150 个会话；没有测过数千并发，也没有测量 `max_conns` 打满时的行为（只有代码层面的实现，没有自动化用例）。
8. **优雅关闭、自定义 DNS 服务器（`dns` 字段）、IPv6 实际链路**：没有专门的自动化用例。
9. **ECH 与真实 CDN/浏览器互操作**：ECH 只在 nakis 自己的客户端与服务端之间测过。
10. **诱饵与真实 nginx 的逐字节对比**：只验证了状态码和内容形态；没有与真实 nginx 的完整响应头对比，已知有差异（SPEC §15）。
11. **NAP（会话结束标记）的可见性**：每个会话结束时双向各有一个孤立的 2 字节帧（TLS 下一条 24 字节的记录），当前版本没有对它做填充，这是一个可被统计的边界特征，**没有对应的测试，也没有被处理**。
12. **吞吐数字不代表真实网络**：回环下的数字只说明每字节 CPU 成本。

import socket, time
def probe(data, wait=6):
    s = socket.create_connection(("127.0.0.1", 18443)); t = time.time()
    s.sendall(data); s.settimeout(wait); out = b""
    try:
        while (c := s.recv(4096)): out += c
    except Exception: pass
    print(f"{time.time()-t:5.2f}s  {len(out)} bytes  {out[:15]!r}")
