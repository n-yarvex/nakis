# Nakis 🍓

> **小窝在这里 →** [Telegram](https://t.me/nakis_proxy)
Nakis 是一个基于 go 开发的 SOCKS5 入口 + TLS 隧道的轻量代理协议（！），抗DPI协议（？），加速器（？）

### 🧺 合包机制（前无古人 零碎的小写入会被攒成大帧再发）

1. **闲时立发**：队列是空的，而且离上一次数据到来已经 ≥ 40µs，这块数据就不等，立刻发走。交互小包靠的就是这条。

2. **忙时才合并**：紧跟着到达的数据进队列，一个帧里贪心地装，装到 `send_pack` 为止。一块数据不会被拆开，装不下的留给下一帧。

3. **满了就发**：队列字节数 ≥ `send_pack`，或者离装满只差 `send_tail`（默认 512 字节），都不再等。

4. **没满就等一拍**：启动 250µs 的定时器，到点后如果这段时间又有新数据到来，且已等的轮数 < `send_quiet × 4`，就再等一拍，否则发出。所以 `send_quiet=4` 的意思是：只要数据还在紧跟着到来，最多持续合并 4ms。数据一断流，最多再等 250µs 就发。

5. **发出就是清空**：反复合并，直到队列清空，每次合并产生一个 DATA 帧，一帧一次 `Write`。TLS 下它在一条记录里。

6. **大块直通**：服务端下行一次读到 ≥ 32766 字节，先冲掉队列里已有的数据保序，再整块直接写出，不合并也不填充。
7. **会话最前面的几个包例外**：先走"首包随机计划"（凑够目标大小再发，不够则 2ms 后补填充），计划用完才回到上面这套规则。

8. **服务端还有第二层合并**：从隧道收到的上行小帧会先排队，合并成至多 `merge_pack`（默认 20480 字节）再一次写给目标。队列涨到 `max_queue` 就停止读隧道，靠 TCP 反压让客户端慢下来。


### 🏁 并发拨号竞速（懒得细说，自己看SPEC去吧）

池里暂时没有热隧道？那就同时试好几个地址（前两个立刻开跑，后面的错开 50 毫秒），**第一个握手完成的赢**；输掉的也不浪费，会收进池里备用。服务端连目标网站也一样，IPv4/IPv6 交错着赛跑，谁快用谁，但可能造成特征？

### 🔥 连接池 + 预连接（没什么可强调的啦，去看SPEC）

池里永远有热好的隧道（TLS 握手早在你点开网页之前就做完了）。想要新会话可以直接拿一条用，**没有握手要等**。这个是**强制开启**的，没有开关，因为关掉只会变慢呀。

### ♻️ 连接复用（没什么可强调的啦，去看SPEC）

会话结束时双方交换一个小小的结束标记（NAP），隧道就干干净净地回到池里，下一个会话接着用，连认证都不用再来一遍。

### 🤝 TCP 半关闭（一端发完，另一端没传完的数据不会被截断）

应用 `shutdown(SHUT_WR)` 之后，目标收到的是一个正常的 FIN，它的响应会完整传回来，不管要等多久；反过来目标先发完，应用后面的上传也照样传完。两个方向各自收尾，都收尾了隧道才回池复用。只有对端一直沉默时才会按 `half_close_timeout`（默认 2 分钟，每收到数据重新计时）回收。应用整个关闭、目标还在灌数据的情况（取消大下载）会很快发现并收尾，不会一直灌到超时。细节见 [SPEC 5.4 / 5.5](doc/SPEC.md)。

### 📞 UDP over TCP（语音通话、QUIC、DNS 等，自动切换）

应用发 SOCKS5 `UDP ASSOCIATE` 时，客户端自动从池里取一条隧道，用一个魔术地址告诉服务端「这条走 UDP」，TCP 请求完全按原有逻辑，不受影响。UDP 数据报在隧道里走一层极简的 mux：它**不追求性能，只做时序扰动**——每一批数据报发出前随机多等 0～`udp_jitter`（默认 8ms）并和这段时间里到达的合并，固定节奏的语音流不会原样出现在线路上。服务端的 UDP 套接字只收它发过包的 IP 的回包，目的地同样受私网拦截约束，`udp: false` 可整体关掉。它不隐藏数据报大小，TCP 承载 UDP 在丢包时会有延迟抖动，限制与边界见 [SPEC 第 17 章](doc/SPEC.md) 和第 15 章。

### 🥷流量长得与众不同就容易被盯上，所以做了好多打扮：

- **首包随机化**：`shape_up` 可以指定上行前几个包（最多八个）的大小（重点：不是靠填充！而是靠合包！），每条隧道、每个会话、每个方向，最多前8个包的大小都重新抽签，并用随机填充补足。80 条新隧道里 72–77 种不同大小，没有任何一个大小占比超过 4%；整形还会看目标端口：目标是 443 这类 TLS 端口（说明隧道里还套着一层 TLS）时，覆盖的包数更多、大包更常出现，不测速、不看网络，只看端口和随机数；
- **ECH**：把真正要连的服务器名藏进加密的握手里，可以规避基于 SNI 的检测，ECH 密钥在配置里就能填，不依赖 DOH。
- **像浏览器的 ALPN**：客户端报 `h2, http/1.1`，服务端按普通网站那样回 `http/1.1`，只伪造ALPN但不使用 uTLS 模拟指纹，因为 uTLS 可能造成可被低成本识别的鹦鹉特性；
- **自适应整形**：按流量类型提前调整，每条隧道还会随机抽一个自己的寿命（会话数在 `[⌈n/2⌉, n]` 里抽、字节数在 8–256 MiB 里对数抽），先到先退役，所以没有固定的「第 N 个会话 / 第 N 字节」可供统计，也不会对已经发生的限速做补救，也没有真实网络的数据，只是去掉一个可统计的边界。
- **诱饵页**：有好奇的路人来敲门，认证失败不会沉默暴露自己（虽然主动探测根本就不存在），只要不是合法的 nakis 客户端，就得到一个 nginx 欢迎页（`/` → 200，别的路径 → 404，乱码 → 400）；


### 🛡️ 安全小细节

- 认证证明是 HMAC-SHA256，绑定了这一次 **TLS 会话**（用 TLS exporter），抓到了也转发不到别的连接；
- **防重放**：nonce 缓存 + 启动时刻检查 + ±30 秒时间窗，缓存满了宁可拒绝也不放行；
- 默认**不允许访问内网 / 回环 / 云元数据地址**，uuid 万一泄露也不会变成别人戳你内网的跳板；


### 🔗 一条链接导入节点（图形客户端用）

`nakis://uuid@地址:端口?参数#节点名`，一行就是一个完整节点（地址、证书指纹、ECH 配置都在里面），只写和默认值不同的参数，未知参数一律忽略，所以以后加参数不会让旧链接失效。订阅就是若干条链接（明文或 base64，每行一条）。格式的完整定义在 [SPEC 第 16 章](doc/SPEC.md)，面向使用者的说明在 [CONFIG 第 4 节](doc/CONFIG.md)。命令行也有 `nakis link`（编码 / 解码）、`nakis sub`（看订阅）、`nakis client -l 链接`（直接用链接跑）。

### 🧰 服务端一键脚本

[`nakis-install.sh`](tool/nakis-install.sh)：只管服务端，装好后自带管理菜单（改配置、看链接和订阅、启停、日志、更新、换 uuid / 证书 / ECH 密钥、体检、卸载）。能交互问的参数都会问（也能全部用环境变量无人值守），装完直接给你分享链接和订阅文本。

```sh
   curl -fsSL https://raw.githubusercontent.com/n-yarvex/nakis/main/tool/nakis-install.sh -o nakis-install.sh && bash nakis-install.sh
```
